# 2. kordoc 으로 파싱한 문서를 Agentic RAG 에 쓸 수 있는가

> 대상: [chrisryugj/kordoc](https://github.com/chrisryugj/kordoc) v4.24.65 (npm `kordoc`, MIT) — HWP·HWPX·PDF·DOCX 등 → Markdown / 구조 청크 / JSON
> 실험 문서: 국가법령정보센터에서 받은 별표 5종 (HWP·PDF 각각) — KGMP [별표 1], 행정처분 [별표 8], 고시 [별표 17]·[별표 13]·[별표 9]
> 재현: `uv run kgmp eval` (검색 실험), 파싱 통계는 `data/index/kordoc_parse_stats.json`

## 결론 먼저

**쓸 수 있다. 다만 kordoc 의 기본 RAG 청크(`--format chunks`)보다 "kordoc Markdown + 법령식 번호 청커" 조합이 낫다.**

| 항목 | 결과 | 판단 |
|---|---|---|
| 텍스트 정확도 | HWP 와 PDF 결과가 공백을 빼면 **5개 문서 모두 100% 일치** | ✅ 원문 손실 없음 |
| 표 | [별표 8] 행정처분 기준표 **340행이 HWP·PDF 모두 같은 구조로** 나옴 (병합 셀 `rowspan` 보존) | ✅ |
| 속도 | HWP 0.3~0.5초, PDF 0.8~2.1초 / 문서 (Node, CPU) | ✅ 수백 건도 수 분 |
| 폐쇄망 | `KORDOC_OFFLINE=1` 로 외부 통신 없이 동작 | ✅ 제약사 내부망 적합 |
| 구조(위계) | 법령 별표는 제목 스타일 없이 "1. / 가. / 1)" 번호로만 위계를 표현 → kordoc 기본 청크의 **50% 가 경로(breadcrumb) 없음**, 일부는 긴 문장이 제목으로 잡힘 | ⚠️ 법령식 청커로 보완 |
| PDF 띄어쓰기 | PDF 는 줄바꿈 자리에 공백이 끼어 **단어 0~2.7% 가 쪼개짐** (예: "처분기준에" → "처 분기준에", 표 셀에 집중) | ⚠️ 가능하면 HWP 원본 사용 |
| PDF 목록 표기 | PDF 결과는 항목을 Markdown 목록(`- 가.`, `  - 1\)`)으로 냄 → HWP 와 표기가 다름 | ⚠️ 청커에서 정규화 |

## 2.1 kordoc 이 RAG 관점에서 주는 것

- **입력**: HWP 3.x·5.x, HWPX, HWPML, PDF(텍스트층 + 내장 OCR), DOCX, XLSX, PPTX, 이미지 — 식약처·법제처 문서 형식을 사실상 모두 커버
- **출력**: Markdown(표는 병합 셀이 있으면 HTML `<table>`), `--format chunks`(제목 경로 + 독립 표 청크 JSON), `--format json`(블록 IR)
- **연동 방식**: CLI(이 데모), Node 라이브러리, Python SDK(`pip install kordoc` — 상주 엔진 워커), MCP 서버(22개 도구 — 에이전트가 사용자가 올린 파일을 그 자리에서 파싱할 때 유용)

## 2.2 실험 1 — 파싱 정확도 (HWP vs PDF)

| 문서 | 크기 HWP / PDF | 시간 HWP / PDF | 한글 글자 수 | HWP·PDF 일치(공백 제외) | 표 행 | 쪼개진 단어(PDF) |
|---|---|---|---|---|---|---|
| KGMP [별표 1] | 103 / 197 KB | 0.34 / 1.08 s | 16,614 | 1.000 | 0 | 27 / 5,128 (0.5%) |
| 행정처분 [별표 8] | 199 / 292 KB | 0.39 / 2.10 s | 32,076 | 1.000 | 340 / 340 | 279 / 10,270 (2.7%) |
| 고시 [별표 17] | 68 / 529 KB | 0.45 / 1.75 s | 34,098 | 1.000 | 0 | 55 / 10,766 (0.5%) |
| 고시 [별표 13] | 28 / 335 KB | 0.39 / 1.11 s | 11,757 | 1.000 | 0 | 9 / 3,441 (0.3%) |
| 고시 [별표 9] | 17 / 249 KB | 0.42 / 0.77 s | 3,710 | 1.000 | 0 | 0 / 1,127 (0%) |

- 같은 문서를 서로 다른 형식으로 넣어도 내용이 같게 나온다 → 원본이 PDF 뿐인 가이드라인도 믿고 쓸 수 있다.
- 단, PDF 는 줄바꿈 때문에 단어가 쪼개진다. 검색은 한글 2-gram 을 쓰므로 영향이 작지만, **근거 문구를 그대로 인용할 때는 HWP 원본이 낫다.**

## 2.3 실험 2 — 청킹 방식별 검색 품질

공정 엔지니어가 물을 법한 질의 16개(수율 이탈, 일탈 조사, 재가공 승인, 변경관리, 행정처분, 회수, 제품품질평가 등)와
정답 조항을 정해 두고, BM25 검색에서 정답 조항이 몇 위에 나오는지 쟀다. 법령·고시 **본문**은 세 경우 모두 같은 조문 청크를 쓰고, **별표** 처리만 바꿨다.

| 방식 | 별표 청크 수 | 경로 없는 청크 | 단일 질의 hit@1 | hit@5 | MRR@10 | 재질의 포함 hit@5 | MRR@10 |
|---|---|---|---|---|---|---|---|
| A. kordoc Markdown(HWP) + 법령식 청커 **(기본값)** | 744 | 0% | **0.38** | **0.62** | **0.485** | 1.00 | 0.880 |
| B. kordoc Markdown(PDF) + 법령식 청커 | 759 | 0% | 0.31 | 0.62 | 0.454 | 1.00 | **0.908** |
| C. kordoc `--format chunks` 그대로 | 256 | 50% | 0.25 | 0.44 | 0.389 | 1.00 | 0.859 |

질의별 정답 순위 (단일 질의):

| 질의 | 정답 위치 | A | B | C |
|---|---|---|---|---|
| 타정 공정이 끝났는데 수율이 기준보다 낮게 나왔다. 무엇을 해야 하나 | KGMP 8.1 사목 | 8 | 8 | 10 |
| 수율관리기준의 정의 | KGMP 1. 자목 | 1 | 1 | 6 |
| 제조기록서에 수율 이탈 사유를 적어야 하나 | KGMP 8.1 가목 5) | 4 | 4 | 7 |
| 예상 수율과 크게 다른 경우 일탈로 처리해야 하나 | 고시 별표17 5.5 마목 | 1 | 1 | 2 |
| 기준을 벗어난 반제품을 다시 가공하려면 누구 승인이 필요한가 | KGMP 8.1 카목 | 1 | 1 | 2 |
| 제조 중 일탈이 생기면 제조부서 책임자는 무엇을 하나 | KGMP 3.2 나목 | 2 | 2 | 7 |
| 제조공정이나 설비를 바꾸려면 어떤 절차를 거쳐야 하나 | KGMP 12. 변경관리 | – | – | – |
| GMP 를 지키지 않으면 어떤 행정처분을 받나 | 규칙 별표8 | – | – | – |
| 품질 문제로 출하한 제품을 회수해야 할 때 절차 | 회수 규정 | – | – | – |

**해석**

1. **법령식 청커가 kordoc 기본 청크보다 낫다** (MRR 0.485 vs 0.389). 기본 청크는 "1. / 가. / 1)" 번호를 제목으로 인식하지 못해 절반이 위치 정보 없이 섞이고(예: KGMP 8.1 제조공정관리의 가~카목이 한 청크), 정의 조항처럼 짧은 조항이 큰 덩어리에 묻힌다. 법령식 청커는 "목" 단위로 나누고 `8 제조관리 > 8.1 제조공정관리 > 사목` 같은 경로를 붙여 **에이전트가 조항 번호까지 인용**할 수 있다.
2. **단일 질의로는 부족하다** (hit@5 0.62). 엔지니어의 일상어("바꾸려면", "회수해야 할 때")와 법령 용어("변경관리", "회수계획")가 달라 키워드 검색이 놓친다. → 그래서 **Agentic RAG** 가 필요하다: 에이전트가 질의를 법령 용어로 바꿔 여러 번 검색하고, 찾은 조항이 가리키는 다른 조항(예: "제4.1호거목의 제조지시서")을 따라 읽는다.
3. 재질의를 흉내 낸 질의(사람이 미리 작성, `evaluate.py` 의 `AGENT_QUERIES`)를 더하면 세 방식 모두 hit@5 1.00 이 된다. **단, 정답을 아는 사람이 쓴 질의라 낙관적인 상한**이다. 실제 LLM 이 만드는 질의로는 `kgmp respond` 실행 결과(인용 조항)를 보고 확인해야 한다.

## 2.4 kordoc 을 쓰면서 보완한 것 (이 데모의 `parse.py`)

| 문제 | 보완 |
|---|---|
| 별표의 위계가 번호로만 표현됨 | `1.` → `1.1` → `1.1.1` → `가.` 까지를 경로로, `1)`·`가)`·`(1)` 은 같은 청크 안에 둠 |
| 긴 목(1,800자 초과) | `1)` 경계에서 나누고 각 조각 앞에 목의 첫 문장을 붙임 |
| 표 | `<table>` 을 행 단위 텍스트로 바꿔 8행씩, 머리행을 붙여 청크 |
| PDF 목록 표기 | `- 가.`, `\)` 등 정규화 후 같은 규칙 적용 |
| 법령 본문 | kordoc 대상이 아님(웹 HTML) → 조문 단위, 긴 조문은 항·호 경계로 분할 |

## 2.5 권장 운영 방식

- **원본 형식**: HWP(X) > 텍스트층 PDF > 스캔 PDF(`--ocr`). 법제처 별표는 HWP·PDF 를 같이 주므로 HWP 를 쓴다.
- **문서 갱신**: 법령·고시는 수시 개정(예: [별표 8] 은 2026-11-10 개정분까지 반영됨) → `kgmp fetch` 를 주기 실행하고 청크에 시행일을 남긴다.
- **가이드라인**: 식약처 안내서는 대부분 PDF/HWP → `data/raw/user_docs/` 에 넣으면 같은 파이프라인으로 색인(위계 5).
- **에이전트 런타임 파싱**: 품질담당자가 SOP·일탈보고서를 올리는 경우 kordoc MCP 서버를 에이전트 도구로 붙이면 그 자리에서 읽을 수 있다.
- **검색 고도화(다음 단계)**: BM25 + 임베딩 하이브리드, 법령 용어 동의어 사전(바꾸다→변경, 다시 만들다→재가공), 조문 상호참조 그래프.
